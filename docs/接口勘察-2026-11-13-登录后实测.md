# 登录后接口勘察（2026-11-13 实测）

真实登录 15583981548 后，在容器内用 Cookie 直接打接口 + 无头浏览器抓包得出的结论。
凡标「实测」的都有明确返回；标「未找到」的是扫遍网页端接口确实没有。

## 一、结论速览

| 项 | 结论 |
|---|---|
| 登录 | 手机号 + 短信验证码，无头 Chromium 可完成（无滑块，一次通过） |
| 健康检查 | ❌ `/alice/profile/self` 对有效 Cookie 返回 `code:710010202 系统错误` |
| 替代健康检查 | ✅ `/alice/commerce/sale/subscription/quota/summary/` 返回 `code:0` |
| 多轮上下文 | ✅ 传 `conversation_id` + `need_create_conversation:false` 即可，无需拼历史 |
| 新会话 | ✅ `need_create_conversation:true`，SSE_ACK 里返回新 `conversation_id` |
| 剩余额度数值 | ❌ 网页端接口没有；只有订阅状态与卡券余额 |
| 签到接口 | ❌ 网页端不存在（扫了 77 条接口，无签到/打卡/领取字样） |

## 二、登录

- 入口：网页右上「登录」→「手机号登录」→ 填号 → 勾协议 →「下一步」→ 6 位短信码
- 关键控件：`[data-testid="login_phone_number_input"]`、`login_next_button`、`login_agreement_check`
- 验证码不点「获取验证码」，点「下一步」即自动下发（页面显示 57s 倒计时）
- 登录成功后写入 31 个 Cookie：`sessionid` / `sid_guard` / `sid_tt` / `uid_tt` / `d_ticket` / `ttwid` 等
- 验证码输入框不是普通 input，`placeholder*="验证码"` 匹配不到；直接 `keyboard.type` 逐字输入即可

## 三、健康检查（重要修正）

```
POST /alice/profile/self?aid=497858&version_code=20800
→ HTTP 200 {"code":710010202,"msg":"系统错误"}
```

同一账号、同一 Cookie，网页端调用却正常。差别在网页端 URL 额外带了 `msToken` 与 `a_bogus` 签名参数
（每次请求现算）。结论：**这个接口不能用来判活**，拿它做健康检查会把好账号误判成失效。

替代方案（无需签名，实测成功）：

```
POST /alice/commerce/sale/subscription/quota/summary/?aid=497858&version_code=20800
→ {"data":{...},"code":0}
```

插件里 `checkAll()` 已改为用后者。

## 四、额度 / 积分

| 接口 | 返回 |
|---|---|
| `/alice/commerce/sale/subscription/quota/summary/` | 仅订阅信息：`display.short_name = "免费体验"`，`hasActiveSubscription:false`，`window_limit_section:{}` —— **没有剩余额度数字** |
| `/alice/commerce/marketing/card/balance/` | `available_count:0`，`quota_reset_card:0`、`pc_quota_reset_card:0` —— 卡券，不是额度 |
| `/alice/commerce/sale/subscription/entry/config/` | 会员入口配置，`click_url` 指向 `/member/subscription` |
| `/member/subscription`（页面） | 只卖套餐（标准 68/月、加强、高级，含 9000 额度/月），不显示我的余量 |

**0.01x 模型实测**：`deepseek-v4.1-flash` 7.2s / `doubao-2.1-lite` 3.5s，均正常返回；
调用前后 `quota/summary` 无变化——说明这两个模型不从这里扣，或扣的是「当天免费额度」而该接口不体现。

> 结论：想显示「今天还剩多少额度」，网页端拿不到。只能靠**自己记录调用次数**估算。

## 五、签到

- 网页端无签到入口：工作模式落地页只有 创意设计 / 操作浏览器 / PPT / 视频内容提取 / 云电脑 / 项目 / 技能 / 插件
- 扫描 77 条 doubao.com 接口，无 `sign/checkin/打卡/领取` 相关路径
- `/samantha/fission/entrance`（裂变/邀请）：`show_entrance:false`
- `/biz/activity/get_pop_window`：只有营销弹窗（新用户礼包类）

**签到大概率只在豆包 APP 内。** 插件侧能做的是额度监控 + 提醒，不是自动签到。

## 六、多轮上下文（本次最有价值的发现）

旧实现：每次请求新建会话，把历史拼成「用户: … AI: …」整段塞进 text。浪费额度且效果差。

实测可行做法：

1. 第一轮正常发，`need_create_conversation: true`
2. 从 `SSE_ACK` 取 `ack_client_meta.conversation_info.conversation_id`
3. 第二轮带上 `client_meta.conversation_id = <该 id>`、`option.need_create_conversation = false`，**只发新的一条消息**

验证过程（同一账号）：

```
A 新建「记住数字 7」        → 回复「好」，conv=38453481703565826
B 复用（local_conversation_id 故意用新随机值）「刚才的数字是多少」 → 回「7」
C 再复用「把它加 35」        → 回「42」   ← 多轮记忆确实累积
```

要点：
- `local_conversation_id` **不需要**与上一轮一致，随便给即可
- `last_section_id` / `last_message_index` 可以留空
- 复用会话时 `messages` 数组里只放本轮新消息

插件已按此实现 `contextReuse`（默认开）：以「模型 + 首条用户消息」做键，
只有在消息**严格追加一条**时才复用，历史被改写/压缩就走新建，避免上下文错位。

## 七、SSE 事件实况（与旧文档的差异）

本轮真实抓到的顺序：

```
SSE_HEARTBEAT → SSE_ACK → FULL_MSG_NOTIFY → STREAM_TIMEOUT_CONTROL
→ STREAM_MSG_NOTIFY → STREAM_CHUNK → SSE_REPLY_END
```

- **文本实际只从 `STREAM_CHUNK`（patch_object==1）出来**；`STREAM_MSG_NOTIFY` 本轮无文本
- `CHUNK_DELTA` 本轮**没有出现**（虽然请求里开了 `support_chunk_delta`）
- 所以「三种事件都累加」不会重复输出——之前的担心不成立，实测两模型输出均无重复段

## 八、风控

无头浏览器在点输入框时出现过 `#captcha_container` 拦截（滑块墙）。
纯接口调用（Cookie 直连）**没有触发**，可正常出流。所以自动化优先走接口，不要走 UI。
